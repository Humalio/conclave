# System specification

Conclave lets independent AI conversations on different machines communicate, work on reviewed tasks, and use a shared vault. The operator must be able to answer four questions: **Who is connected? What may they do? What have they done? What needs me now?**

The [platform requirements](requirements.md) describe supported behavior and link to subsystem contracts and acceptance checks. The Conclave project's [Blueprint](blueprint.md) holds its backlog, decisions, milestones, risks, and verification status.

## Functional design

Organize daily work around **the record being changed and the person or agent who acts next**. A project gives people the plan and its evidence. A team carries out the work. Needs you brings a person to decisions they can make across those records. A collaborator sharing only notes can start and finish in Vault.

| User requirement | What the user should be able to do |
|---|---|
| Start in the right place with the right access | After setup, a collaborator can open their project or shared folder. The operator can tell whose agent is connected and check whether that agent may perform a particular action there. |
| Follow work from intent to result | From a requirement or research question, follow its recorded links to the relevant work and evidence. A worker can tell what to pick up or resume. At hand-off, the next participant can identify the task, the current submission and the action due. |
| Decide once, in context | From Home, a project or a team, a decider can find the same outstanding question, proposal or checkpoint, inspect what their choice affects and act within their authority. A successful answer updates the source and every view of it. A failed read is visible as a failure. |
| Work together without losing a contribution | A person editing a shared note can tell which text was saved, keep their newer edits and resolve a conflicting revision. A submitted task can pass to an eligible replacement reviewer without making the worker repeat the submission. |
| Tell what actually happened | The operator can distinguish a connected session, a picked-up task, a submitted result, an independent verdict and a human decision. The relevant record identifies who acted and what version or evidence the action concerned. |

For example, a worker asks a question that blocks a task. The team's decider opens the question from Needs you, sees the affected task and answers once. The answer remains on the question, the task resumes its previous turn where valid, and the agent can continue on its next turn or through its connector if wake is enabled. The operator can later trace the pause and the answer from those records. [Decisions](decisions.md) · [Task hand-offs](mcp.md#team-modes)

The [workflow repair package](workflow-repairs.md) identifies the gaps demonstrated against this model and proposes acceptance cases for the next release.

## Scope

Run one self-hosted hub with a SQLite database, an Obsidian-compatible vault, a web console, and a stateless Streamable HTTP MCP endpoint. The connector runs on each enrolled computer, where it connects agent sessions and can transfer files from approved folders. A computer can run several independent agent conversations. Work waits for an agent's next turn unless the PC user has enabled the connector to start a background turn for that agent.

The target desktop workflows are Claude Code, Claude Desktop, and Codex. Client configuration and validation status belong in the [MCP guide](mcp.md#client-setup). Guest access, OAuth, browser and cloud AI connectors, direct peer-to-peer transfers, and multi-instance operation are outside scope. The vault works as a plain local directory without Obsidian or a sync provider. Hosting, TLS, network exposure, and external synchronization are operator responsibilities.

## Trust model

- **L0** is hub control text, the operator's playbooks and notes, and Blueprint items written by the operator or the docs import.
- **L1** is scoped delegated work: task and review content, and Blueprint items written by an agent of the reader's own team.
- **L2** is peer data: messages, files, shares, transfer content, derived claims, and Blueprint items written by an agent of another team.

Carry provenance on work and data payloads, and never let embedded L2 text become policy or raise authority. The [threat model](threat-model.md) lists the boundaries and the remaining risks.

## Who may message whom in a team

When a team grants messaging, the hub links these pairs, and each pair may send and receive direct messages both ways: the coordinator with each worker, each stakeholder, each reviewer and each curator, and each worker with each reviewer. Workers do not message one another, and reviewers do not message one another: such a message is refused with the reason and what to use instead ("Workers don't message one another: post in the team room or message the coordinator."), while anyone outside the team gets the generic refusal. The links are recomputed from the current members whenever the team changes. A hub that is upgraded adds the coordinator-reviewer and coordinator-curator pairs to every live team on start, with no reset.

## Renaming a team

The operator renames a team in its Settings (**Team**, **Name**, Rename); `PATCH /api/teams/:id` with `name` does the same. The hub checks the name, not only the console: trimmed, 1 to 80 characters, and not another team's name (case-insensitive), or the change is refused with a plain message and nothing changes. A rename keeps the team id, renames the team room, writes one `team.rename` audit event (old and new name) and gives each member one `team_renamed` notice. `team_info` shows the new name at once. The CLAUDE.md or AGENTS.override.md on a PC is not rewritten from the hub: it keeps the old name until the next setup or resume, and the notice says so. Agent labels do not change, because they come from the project.

## Sharing files from a team

Workers and coordinators may create shares, upload to them and close them (`share_create`, `share_upload`, `share_close`), so evidence such as screenshots travels through the hub and not as a path on one PC. A share goes only to agents the author may message: for a worker, its reviewers and the coordinator. A reviewer, and a coordinator who reviews, read and comment on the shares made for them, and the reviewer of a task in review can always open the share the task names. Reviewers do not create shares. A hub that is upgraded adds these grants to every live team on start, with no reset.

**Task attachments.** A task carries files in two sets: the **brief** (screenshots, mockups and notes for the work, added by the task's creator, a coordinator or the operator with `attachments` or `attachments_from` on `task_create` and `task_update`) and the **submission** (the evidence the assignee hands in with `task_submit`). Each set is a share the hub makes and binds to the task. A new brief version keeps the earlier files and adds or replaces by path; each submission is a round of its own, and the task names the round under review. Inline files are at most 1 MB per call; larger files go first to a share of the caller's own and are copied in with `attachments_from` (or `share_id` on `task_submit`), which takes **only a share the caller made**, still open; the copy never changes who reads the original. Who reads a task's attachments: the operator, and the agents of the task's team who are its coordinator, creator, assignee or reviewer, checked on every read, so a former assignee or a replaced reviewer is refused at once, and nobody reads them once the task is cancelled or discarded. Other agents of the team see how many files there are, a project member's board shows the count and never a file, and an external member sees nothing. The share tools read a task's attachments (`share_info`, `share_read`, `share_diff`, `share_download`) and refuse every other change: comments belong in the review. `share_list` does not list them. `share_read` returns a PNG, JPEG, GIF or WebP up to 5 MB as an image, labelled as L2 data like every attached file. Limits: 8 MB a file (an HTML mockup 2 MB), 40 files and 50 MB a version, 200 MB a task, and 5 GB a team, which the operator can raise in the team's limits (`attachment_bytes`); at 80 % of the team's limit the operator's Needs you list shows it, and at the limit new attachments are refused and an alert is raised. Lockdown refuses new attachments. The console serves a file at `GET /api/tasks/:id/attachments/:role/file?path=…&v=…` to the operator only (a project member and an external member are refused; agents read through the share tools). The hub decides how a file is shown from its bytes, never its name or the type its author gave: a PNG, JPEG, GIF or WebP is shown as an image; an HTML file is shown only when the request says `as=mockup`, in a sandboxed frame with no script, no network and no forms, and without `as=mockup` it downloads; everything else, SVG included, downloads. A set the operator removed answers `not_found`. **Task read access.** A task's assignee and reviewer read what the task needs without an access request, as a live check on every read (no grant is stored, so nothing is left to clean up): they read the task's attachments, and the vault notes the task names in `notes` (`task_create` and `task_update`, at most 10 paths, a coordinator sets them; the submitted evidence is a copy the hub keeps with the task, so it is an attachment and only a share its submitter owns can be copied in), while they hold that role and the task has not ended (done, cancelled or discarded). A replaced reviewer, a released assignee and everyone once the task is done are refused at once. A note counts only if the person who named it could read it at that moment (a note they cannot read is refused when named, so a task cannot hand out a note its writer could not open), and only inside the paths the task's team is given (its own path rules, checked again on every read, so a note the team no longer covers stops reading). An operator's deny rule or a reserved folder is never overridden. The access is read only: no write, no comment, no promote. Every read through this path (`task.note_read`, `task.share_read`) and every change of `notes` (`task.notes`) is audited. A done task keeps its attachments for its creator and coordinators; a cancelled or discarded task's attachments close at once and are deleted 30 days later, audited.

## Task lifecycle

A team task moves through these statuses. The requirements behind them are `FR-TEAM-*` in the Blueprint; the [MCP guide](mcp.md#team-modes) has the agent's side.

| Status | Meaning | Who moves it on |
|---|---|---|
| `backlog` | Proposed; waits for the operator. Agents can read it, and a coordinator can edit it (`task_update`). | Only the operator: **accept** (→ `open`) or **discard** (→ `discarded`), each with an optional note. |
| `open` | Accepted work, ready to assign or claim. | A coordinator assigns it (`task_assign`) or a worker claims a claimable one (`task_claim`). While it is open, the operator can **demote** it back to `backlog`. |
| `assigned`, `in_progress` | An assignee holds the task. Assigned work is queued until started. | The assignee: `task_start`, `task_progress`, `task_submit`. Other team members may add a contributor note with `task_progress {note}`, which changes nothing else. |
| `in_review`, `changes_requested`, `approved` | Submitted work under independent review. | The reviewer (`task_review`), then the coordinator or the operator's done checkpoint (`task_complete`). A coordinator may send an approved task back (`task_reopen`), below. |
| `blocked` | Waits on a question or an outside cause; returns to the status it was blocked from ([decisions](decisions.md)). | `task_unblock`, or the answer to its `team_ask`. |
| `done`, `cancelled`, `discarded` | Ended. `discarded` is a proposal the operator turned down; it stays for history. | Nobody. |

- **Intake.** Each project has a task intake, `backlog` (the default) or `open`, set by the operator (`PATCH /api/projects/:id {task_intake}` or a team's settings; audited as `blueprint.task_intake`, and the coordinators get a notice). With `backlog`, an agent's `task_create` lands in `backlog`; with `open`, it opens at once. A team without a project counts as `open`. Changing the intake does not change existing tasks. When the operator moves a team to another project (`PUT /api/teams/:id/project`) and that changes where its new tasks land, the team's coordinators get a notice too.
- **Relayed requests.** A coordinator who creates a task because the operator asked for it passes `operator_request {source}`: the task opens at once, is stored as relayed (L1, like a relayed `team_ask` answer) and is shown as opened on the operator's relayed request. It is audited as `task.operator_request`, and the operator may demote it: `GET /api/tasks/backlog` also returns `relayed`, the tasks opened this way in the last 7 days that nobody holds yet, and Home's Backlog card lists them with **Back to backlog**.
- **Backlog refusals.** In `backlog` or `discarded`, `task_assign`, `task_claim`, `task_start`, `task_progress` and `task_submit` fail with `invalid_state` naming the operator's accept, and `work_next` skips the task. A coordinator cannot block or cancel a backlog task, and `team_ask` cannot block one, so it leaves the backlog only through the operator.
- **Operator moves.** Accept, discard and demote are admin-only (`POST /api/teams/:id/tasks/:taskId/accept|discard|demote {note?}`; `GET /api/tasks/backlog?list=active|postponed&project=<id>&team=<id>&tag=<tag>&q=<text>&limit=&cursor=` lists the waiting tasks of every team, oldest first; `q` keeps the tasks whose title or brief contains the text, ignoring case (SQLite LIKE, so ASCII letters only), and applies before paging and the counts, like the other filters); there is no MCP tool for them. Each records a task event, is audited (`task.accept`, `task.discard`, `task.demote`, with the note) and sends an L0 notice (`task_accepted`, `task_discarded`, `task_demoted`) to the creator and the team's coordinators.
- **Postponed.** The operator can **postpone** a backlog task and **return it to active** (`POST /api/teams/:id/tasks/:taskId/postpone|restore {note?, version?}`, admin-only, no MCP tool). A postponed task stays `backlog`: only its `postponed_at` time is set, so every backlog refusal above still applies and nobody can assign, claim or start it. Both moves raise the task's version (a stale `version` is `conflict`), record a task event (`admin_postpone`, `admin_restore`) and are audited (`task.postpone`, `task.restore`, with the note). They send no notice: nothing changes for the team. Accept and discard work on an active or a postponed task and clear `postponed_at`; a demoted task starts active. Home's Backlog card, Needs you and the counts of work waiting for the operator take only active backlog tasks. `GET /api/tasks/backlog?list=active|postponed&project=&tag=&limit=&cursor=` applies the list, the project and the tag together before it pages and counts: `total` is the matching tasks of the chosen list, `active_total` and `postponed_total` the matching tasks of each list, `all_total` the whole active backlog, and `tags` and `projects` count the chosen list. The relayed tasks (`relayed`) are open, not backlog: they keep their own group, filtered by project and tag, and are never postponed.
- **Tags.** The creator files a task under 1 or 2 tags in `task_create` (the directives tag model: lowercase, spaces become dashes, only `a-z 0-9 . _ -`, each 1-24 characters, longer ones cut, duplicates dropped; more than 2 is `invalid_argument`). **A project's tag list.** The operator may fix a list of at most 7 tags per project (Project settings → Tags, admin only; `projects.task_tags`, each a lowercase word and a display name; tasks only, not directives). Where a project has a list, `task_create`, `task_update` and the operator's tag edit take only list tags, each task has 1 or 2, and a refused tag gets an answer naming the allowed ones; `team_info` and the coordinator's playbook name the list. Without a list (and for a team without a project) tags are free, at most 2 per task and at most 7 different tags in use across the project: a task that would bring in an eighth is refused, naming the seven and pointing to Project settings. A project already over 7 keeps its tasks as they are and shows a "More than 7 tags: set a list" note in Project settings until it is mapped. An eighth entry in a list is refused ("change the list and retag the tasks"). Changing a list runs a one-time map (`GET|PUT /api/projects/:id/task-tags`, `POST .../preview`; admin-only): each old tag maps to a list tag or is left unmapped; the preview names the dropped tags, the tasks that lose a tag and those left with none, and nothing is saved before it. On save the map runs over every task of the project, done ones included; each keeps at most two tags in list order. It is one audit entry (`project.task_tags`) plus one task event (`admin_tag_map`) per changed task and does not raise task versions. The creator or a coordinator replaces them with `task_update` while the task is in `backlog`; after that an agent's change is `invalid_state`. The operator sets them on any task (`PUT /api/teams/:id/tasks/:taskId/tags {tags, version?}`, audited as `task.tags`, a task event `admin_tags`). Filters by one tag: `task_list {tag}`, `GET /api/tasks/backlog?tag=` (both lists; `tags` counts every tag there, `all_total` the whole backlog) and `GET /api/teams/:id/tasks?status=&tag=` (members: teams whose tasks their grant includes).
- **Short summary ("In short").** Besides its description, a task has a `short_summary`: one or two plain sentences, at most 280 characters, no Markdown. The coordinator sets it with `task_create` or `task_update` (the `task_update` rules apply: not on a terminal task); `""` clears it. Without one, the hub cuts its own from the start of the description, and task views carry both (`short_summary`, `short_summary_hub`). The operator may set or clear it in any status (`PUT /api/teams/:id/tasks/:taskId/short-summary {short_summary, version?}`, audited as `task.short_summary`). The operator's task screen shows it as **In short** above the progress. It is not the assignee's `summary` from `task_submit`. See [MCP](mcp.md), Task summary.
- Tasks the hub raises itself (knowledge flags) open at once, whatever the intake: the hub, not an agent, raised them. They are assigned to the flag's owner when that agent works on tasks (a worker, coordinator or curator, never a reviewer or stakeholder), else claimable. Unlike `task_assign`, they may go to a curator. They always need review, whatever the project's review policy.
- Team progress, a requirement's task count ("n of m done" on the plan and the Blueprint item) and the `tasks_open` metric leave backlog, cancelled and discarded tasks out.
- **Review rounds.** Each request for changes is a round, and so is a coordinator's `task_reopen`. The team's limit (`max_review_rounds`, 1 to 20, default 3; the console labels it "Most review rounds per task") is the most rounds a task gets: with a limit of 3 the first and second requests for changes send the task back, and the third blocks it instead (`Review round limit reached (3 of 3).`) and alerts the operator, who unblocks it to give it back. Replacing a submission while it is in review is not a round.
- **Evidence the reviewer cannot open.** A reviewer who cannot open a share or file the task names asks for changes with `reason: "evidence_unreadable"`. The hub checks it against its own read rules: the submitted share and the task's brief and submission files. If the reviewer really cannot read one of them, the round is not counted, the task goes back to its assignee as usual, the event says what could not be read, and the operator gets a `review_evidence_unreadable` alert, because a task's reviewer can always read them. If everything opens, the request counts as an ordinary round.
- **Sending approved work back.** A merge or release test can fail after approval. The coordinator then moves the approved task back to `changes_requested` with `task_reopen {task_id, reason}`: the reason becomes the review comments, the assignee is handed the task, it counts as a round (the limit above applies), and it is audited as `task.reopen`. A `done` task stays ended and is refused with `invalid_state`: the fix is a new task that names the old one.
- `discarded` is ended like `done` and `cancelled`: the operator can hide it from the board, and retention prunes its history 180 days after its last change, as for the other two.

### Task turns and deadlines

A turn records whose action is next. Assignment or requested changes queues work for the assignee. Starting opens a work turn, and submission opens a review turn for the reviewer. A transition closes the previous turn. A turn is **seen** only when its holder reads that task in full or acts on it: a successful `task_list {task_id}` for that task, a `work_next` item that delivers it, or a successful task call by the holder on that task while the turn is open (`task_start`, `task_progress`, `task_submit`, `task_withdraw`, `task_review`). A list fetch, any other call and a refused attempt leave it unseen. Seen, started and reviewed stay separate: seen is the turn's `seen_at`, started is the task's `started_at`, reviewed is the review event.

- **Queued work** has no work deadline. The work clock starts at `task_start` or a claim with `start: true`. A review turn records a due time from the hand-off.
- **Polling teams** track liveness by member. The deadline is `lease_minutes` after the later of the member's last activity and their declared busy time. When that deadline passes, one sweep returns the member's queued and in-progress assignments to open and notifies the member and coordinators. Each released task records who it lapsed from, when and the status it held (`lapsed_from`, `lapsed_at`, `lapsed_status`); the submitted work, review comments and reviewer stay.
- **Holds stop the sweep.** While the operator holds a member, nothing of theirs is swept: a paused team, a lockdown of all agent writes, of the team, of the agent or of the PC its key is bound to. No lease lapses and no started task is flagged overdue. When the hold lifts, the member's lease restarts from then, as on a team resume (on demand, check-in times move by the time the hold lasted). The hold itself never costs anyone their work.
- **Going quiet on purpose.** A polling member who expects to be silent longer than the lease (a long build, a test run) declares it with `task_progress {until}`: the lease counts from the later of their last activity and that time. An assignment to a member who is already silent past the lease is released by the next sweep, so the coordinator wakes that member first or assigns someone active.
- **Taking a lapsed task back.** For 24 hours the worker it lapsed from may take it back with `task_claim`, even if it is not claimable, while it is still open and unassigned and the worker is still a live member of the team with the worker role and a valid key. The worker holds it again in the status it lapsed from: a queued task comes back queued, a `changes_requested` task comes back with its review comments, and an in-progress task restarts its clock. Anyone else still needs an assignment; a claimable task stays claimable the normal way, for that worker too once the 24 hours have passed. Any move out of open (an assignment, a claim, a cancellation or a block) clears the record, so a coordinator's reassignment in the meantime wins. Both notices say until when the worker may take it back.
- **On-demand teams** flag started work after its check-in time and keep it assigned. Queued tasks do not raise overdue alerts. Use the hand-off result to tell the person running the next session which task to start, continue, or review.
- **A reviewer is away or delegated.** A member away for a one-agent checkout ([checkout](checkout.md) F1) gets no new assignment (`agent_away`) and no claim; its held tasks keep it as holder, and the lease, stall and overdue sweeps skip it. Its reviews go to a replacement reviewer by the rule below, and when nobody is eligible the review waits for it (event `reviewer_away`). While delegated to a collaborator (contributor mode) it takes only tasks assigned to it by name and is no one's reviewer.
- **A reviewer leaves.** When a task's reviewer is removed from the team, the review goes to the next member who may review it, by the same rule as `task_submit`: a reviewer first, then a coordinator when the team lets coordinators review, never the assignee, and only with an active key. A task in review keeps its assignee, its submitted version and its evidence; the old review turn closes (`reassigned`) and one review turn opens for the replacement, who gets the review like any other (a `work_next` item, or a notice in an on-demand team). When nobody is eligible, for example when the only coordinator is the one who submitted, the task stays in review with its author and no reviewer (event `reviewer_removed`), and the coordinators are told to name one with `task_update {reviewer}`. Submitted work never reopens unassigned for want of a reviewer.
- **An author leaves.** Removing a member frees their queued, started and blocked tasks to open, but a task they submitted stays in review with them as its author, and the review goes on. Approval works as usual. A request for changes, or a coordinator's `task_reopen` after approval, returns it to open with the review comments (a counted round), and the coordinators are told to reassign it.
- **Pause** suspends the applicable clocks until the team resumes. A pause may name an end time, at most 24 hours ahead, when the team resumes by itself. A coordinator may set such a pause and end it early; only the operator ends other pauses or sets longer ones.

See [MCP team modes](mcp.md#team-modes) for the tool result and [acceptance](acceptance.md#task-turns) for coverage.

## Keywords on projects and teams

The operator filters the Teams card on Home by keyword. See [dashboard UX](dashboard-ux.md).

- **The known list** is one hub setting, `keywords.known`, starting as "Research & Development" and "Applications" (`GET` / `PUT /api/settings/keywords`, admin-only, audited as `keywords.update`). A keyword is 1 to 40 characters, unique ignoring case and not "All"; at most 20. A keyword left out of a save comes off every project and team that had it, in the same transaction, and the answer says how many (`removed`).
- **Projects and teams** carry known keywords only (`keywords` on `POST` / `PATCH /api/projects` and `/api/teams`; audited as `project.keywords` and `team.keywords`). Every project and team that existed before migration 0103 is "Research & Development", and a new one gets it too, whatever creates it, while that keyword is on the list; a create call that names its keywords replaces the default.
- **Matching.** A team matches a keyword when the team or its project has it. Agents in no team match only All.
- **Agents.** No MCP tool reads or writes keywords, and no MCP result carries them.

## Target platform requirements

These requirements define the intended platform behavior. Use the stable requirement IDs in design reviews and acceptance checks. The [platform requirements catalog](requirements.md) and subsystem guides describe the supported contracts.

### Project structure and Blueprint scope

- <a id="spec-project-01"></a>**SPEC-PROJECT-01 · Projects and ecosystems.** A project represents one body of work. Several teams can contribute to the same project and its Blueprint. An ecosystem can group independent projects so the operator can see how they fit together. An ecosystem holds a shared vision and an overview of its projects; it has no teams or tasks of its own. For example, three teams developing one product can share a Blueprint, while three independent products can appear together under an ecosystem and each retain their own Blueprint.
- <a id="spec-project-02"></a>**SPEC-PROJECT-02 · Team scope.** A team writes only within its own project's Blueprint, in the project-level items and its own part as the write rules allow. Belonging to the same ecosystem gives no access to another project.
- <a id="spec-project-03"></a>**SPEC-PROJECT-03 · Single-team scope.** When the operator sets a project to single-team, the project accepts no second team, and its Blueprint is presented as one list of project and team items, even if other projects share its ecosystem.
- <a id="spec-project-04"></a>**SPEC-PROJECT-04 · Project kind.** The operator can choose **Implementation** or **Research** in project settings.

### Blueprint discovery and detail

- <a id="spec-blueprint-01"></a>**SPEC-BLUEPRINT-01 · Project information.** The Blueprint identifies the project and its kind. **Foundation** opens the project information page and carries no count.
- <a id="spec-blueprint-02"></a>**SPEC-BLUEPRINT-02 · Browse and act.** The operator can search and filter large Blueprint sections, inspect individual items, and take the actions available for each item. Each view provides enough context to identify the item and its relationship to the surrounding work.
- <a id="spec-blueprint-03"></a>**SPEC-BLUEPRINT-03 · Requirements and Acceptance.** **Requirements** opens requirements, and **Acceptance** opens acceptance criteria.
- <a id="spec-blueprint-04"></a>**SPEC-BLUEPRINT-04 · Research labels.** Research sections use labels that describe the research content shown.
- <a id="spec-blueprint-05"></a>**SPEC-BLUEPRINT-05 · Count accuracy.** A selectable count is calculated from the same item types, project or team scope, and filters as the list it opens. For example, **Open 12** opens a view containing 12 matching items, even if they are spread across pages.
- <a id="spec-blueprint-06"></a>**SPEC-BLUEPRINT-06 · Empty counts.** Requirements, Acceptance, and Milestones omit `0/0` indicators.
- <a id="spec-blueprint-07"></a>**SPEC-BLUEPRINT-07 · Dropped items.** The dropped view groups items by their originating section and omits empty groups. The operator can keep an item there for traceability or remove it from ordinary Blueprint views when it no longer helps people understand the work.
- <a id="spec-blueprint-08"></a>**SPEC-BLUEPRINT-08 · Risk details.** A risk page presents likelihood, impact, and owner close to its title. Short Records content is visible as soon as the item opens.
- <a id="spec-blueprint-09"></a>**SPEC-BLUEPRINT-09 · Milestone details.** A milestone page leads with its title and description, and displays task progress when it has linked tasks. A milestone may carry a short name of up to 24 characters, shown in a paper's Delivers line.
- <a id="spec-blueprint-10"></a>**SPEC-BLUEPRINT-10 · Rules.** The operator may let a team apply named kinds of Blueprint change without a proposal. Each applied change names the rule, the operator sees them for awareness, and nothing touching keys, rights, goals, the spec or deletions can be a rule. The one rule is **Release notes** ([ADR-006](decisions/006-blueprint-rules.md)).

### Operator attention and backlog

- <a id="spec-attention-01"></a>**SPEC-ATTENTION-01 · Notice destinations and dismissal.** A notice opens the record or workflow it concerns. For example, a notice about moving a team opens the relevant team or move workflow. The operator can dismiss informational notices that no longer need attention. Dismissal is per viewer.
- <a id="spec-attention-02"></a>**SPEC-ATTENTION-02 · Stalled-member notices.** The operator can enable or disable stalled-member warnings per team, with the default set to off.
- <a id="spec-attention-03"></a>**SPEC-ATTENTION-03 · Missed-milestone notices.** Missed-milestone notifications default to off and are set per project. When one is shown for awareness, the operator can dismiss it.
- <a id="spec-attention-04"></a>**SPEC-ATTENTION-04 · Actionable review queue.** **Needs you → Review** opens the entries represented by the count. Each entry explains what needs attention and provides the actions available to the operator. A resolved entry leaves both the queue and its count.
- <a id="spec-attention-06"></a>**SPEC-ATTENTION-06 · Unclear requirements.** A team marks a requirement unclear by asking the operator one question that names it. Needs you shows that question once, to the person it is routed to, and answering it with **Clarify** also clears the mark. A requirement marked unclear with no question is the administrator's, who can ask the team what is unclear, edit it or drop it.
- <a id="spec-attention-05"></a>**SPEC-ATTENTION-05 · Later.** A decision that waits for the operator can be set aside for later, per viewer, for at most a week or until it changes. It still waits, it stays listed under **Later**, and it returns by itself.
- <a id="spec-backlog-01"></a>**SPEC-BACKLOG-01 · Backlog discovery.** The operator can use project and tag filters together. Backlog rows render supported Markdown and show the full **In short** summary when it fits within four lines. The task detail makes the full summary available.
- <a id="spec-backlog-02"></a>**SPEC-BACKLOG-02 · Backlog postponement.** The operator can accept, discard, or postpone a backlog item. A postponed item remains pending and is available under **Postponed** in the backlog list. Home shows active backlog items, so postponed work stays out of the immediate intake queue.

### Collaboration and project setup

- <a id="spec-collaboration-01"></a>**SPEC-COLLABORATION-01 · Implementation collaboration.** Collaborators can work together on one or several implementation projects. Their agents can participate in the same team or work in separate teams, according to how the work is organized.
- <a id="spec-collaboration-02"></a>**SPEC-COLLABORATION-02 · Research collaboration.** Collaborators can quickly find existing and planned papers, see the status and activity of hypotheses, and inspect the experiments behind them. A milestone or hypothesis can relate to multiple papers. A collaborator can use either relationship to filter the paper list and see which papers depend on the same work.
- <a id="spec-collaboration-03"></a>**SPEC-COLLABORATION-03 · Vault collaboration.** Collaborators and their agents can work with authorized shared vault content independently of an implementation or research project. Human access follows the collaborator's grant, and an agent's actions follow both the permissions granted to that agent and its owner's delegated grant. An agent never acts beyond its owner's grant, including through work it asks other agents to do.
- <a id="spec-collaboration-04"></a>**SPEC-COLLABORATION-04 · Collaborator landing.** A collaborator with access to exactly one project and one team lands directly on that project. A collaborator with only vault folder access lands in Vault. Anyone else lands on Home with their destinations. An explicit link always wins.
- <a id="spec-collaboration-05"></a>**SPEC-COLLABORATION-05 · Collaborator account.** The Account page uses **Collaborator** as the role label and makes the person's account and access easy to understand.
- <a id="spec-collaboration-06"></a>**SPEC-COLLABORATION-06 · Empty vault.** An empty collaborator Vault view uses the available width and clearly describes the empty state.
- <a id="spec-onboarding-01"></a>**SPEC-ONBOARDING-01 · Requirements setup.** Onboarding asks whether requirements already exist and where they can be found, whether the coordinator should derive them, or whether the operator will supply them. The team can tell which source to use or who is responsible for providing the requirements.
- <a id="spec-onboarding-02"></a>**SPEC-ONBOARDING-02 · Research paper setup.** Onboarding captures both existing and planned papers. The hub records them as part of the research project so the team can find them, track their state, and keep them current.

### Vault content and agent pages

- <a id="spec-vault-01"></a>**SPEC-VAULT-01 · Vault previews and playback.** Authorized viewers can preview image files, browse folders containing audio clips, and play audio embedded in a vault note. For example, a meeting note can embed its recording and let a reader play it from the note.
- <a id="spec-vault-02"></a>**SPEC-VAULT-02 · Vault links.** Links to vault files open the intended file, and relative file links resolve from the folder containing the note.
- <a id="spec-content-01"></a>**SPEC-CONTENT-01 · Markdown.** Blueprint criteria, backlog summaries, and other Markdown-bearing fields display their supported formatting correctly in the context where they appear.
- <a id="spec-agent-01"></a>**SPEC-AGENT-01 · Agent inbox.** The agent page has a dedicated area for messages from the hub, separate from activity.
- <a id="spec-agent-02"></a>**SPEC-AGENT-02 · Team playbooks.** The agent page gives the operator access to the complete team playbook, including long playbooks.

### Hardware

- <a id="spec-hardware-01"></a>**SPEC-HARDWARE-01 · Inventory and availability.** The Hardware area lists machines registered for agent work. It shows when each machine is available and which shared-use limits apply, including memory where configured.
- <a id="spec-hardware-02"></a>**SPEC-HARDWARE-02 · Usage and waiting work.** The operator can see which agent holds a machine, the task, the estimated duration, and which work is waiting. Where the machine's user has turned measuring on, the operator also sees the machine's CPU, memory and GPU use, now and during each hold. These figures are the whole machine's, not proof of what the agent ran. Without measuring, use is what the holder reports.
- <a id="spec-hardware-03"></a>**SPEC-HARDWARE-03 · Registration and access.** The operator can register a machine for agent use through an assisted setup flow. The system supports machines accessed through existing SSH arrangements.

### Agent feedback

- <a id="spec-fdbk-01"></a>**SPEC-FDBK-01 · Reports and the tasks that fix them.** A report can be linked to the tasks that fix it. When every linked task is approved and done, the report is marked fixed for the next hub version, and the operator can still reopen or correct it.

## Audit trail and database health

The audit trail is append-only. No audit row can be changed, and no row younger than the audit horizon can be deleted; the database enforces both. Only the operator can move the horizon, through the **Audit trail** clean-up rule (off by default), and only forward and never to less than 365 days ago. Before any row leaves the hub, the rule archives it to a compressed file beside the backups, with a hash chain that proves the file whole and in order. It also records one `audit.trimmed` event naming the file, its sha256 and the date range, and that event is never removed. The last 365 days of security history therefore always stay in the hub.

The other clean-up rules (activity, revoked keys, finished items, stale PCs and agents, and the by-hand revoke of long-suspended keys), the backups, integrity checks and compaction are in **Security → Database**; see [operations](operations.md). Every run takes a backup first, removes exactly what its preview listed, and is audited. A revoked key leaves a tombstone, so its reuse still raises the reused-key alert. An agent with any record it wrote is never removed.
